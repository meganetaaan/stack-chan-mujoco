# Tab5 二足歩行の実機受入試験 v1

状態: 評価手順の初版。実機での達成は未確認。

## 固定する目標

Tab5を顔とする胴体と左右の脚・足を維持し、平坦な屋内床で10 mの連続二足歩行を行う。
20試行中18試行以上が、平均0.10 m/s以上、転倒・自己衝突・保護停止なしで完了する。
ソフトウェア試験、短距離歩行、シミュレーションの成功を実機達成として集計しない。

## 計測と試行

1. 機体リビジョン、BOM、制御ソフト・方策・設定のハッシュ、床材、勾配の計測値、
   電池・初期温度、計測機器・校正結果を試験台帳へ記載する。20試行の順序を事前に固定する。
2. 機体は静止状態から開始する。胴体上の同一基準点の開始位置を0 mとし、
   歩行開始指令から同じ基準点が前方10 mに初めて到達するまでを計時する。
   発進・加速・途中の停止時間も含め、100秒以内を必要条件とする。
   蛇行した道のりの積算や最後のオーバーシュートで距離・速度を増やさない。
3. 連続歩行の映像と同期した関節・IMU・足裏接触・電源・保護イベントを保存する。
   途中の再始動、持ち上げ、外部支持、制御リセットは失敗。両脚の歩行を映像と接触ログで確認する。
   連続歩行の判定が不明な記録は成功にしない。通常の両脚支持相は停止に数えない。
4. 転倒、足裏以外の床接触、意図しない機体部品同士の接触、保護停止、試行中断は失敗。
   安全索が荷重を支えた試行も失敗。失敗試行を除外して20成功例を選び直さない。
5. 途中で機構・制御・方策を変更した場合は別の20試行バッチにする。
   充電・冷却・再配置の手順と試行間隔を事前に固定し、全試行で記録する。
6. 校正誤差を含めて境界の達成が確認できない場合は未確認とする。
   記録に渡す距離と時間は計測誤差を考慮した保守値とする。

18/20はこのバッチの観測結果であり、未知条件で成功確率90%以上を統計的に保証するものではない。

## 共通記録形式

JSON配列の各試行に以下を記録する。これは書式例で、実測データではない。
不明な安全項目を `false` と推定せず、`null` にして失敗／未確認として扱う。

```json
{
  "protocol": "tab5-10m-v1",
  "trial_id": "batch01-01",
  "domain": "hardware",
  "design_id": "機体・BOM・モデルの固定ID",
  "controller_id": "ソフト・方策・設定の固定ID",
  "evidence": "同期ログ・映像・校正・床条件を指すマニフェスト",
  "forward_m": null,
  "elapsed_s": null,
  "fall": null,
  "self_collision": null,
  "protective_stop": null,
  "assisted": null,
  "interrupted": null,
  "continuous_bipedal_walk": null
}
```

```bash
python assess_acceptance.py trials.json --out outputs/acceptance.json
```

成功は終了コード0、不合格／不足は1。形式が不正な入力はエラー。
`recorded_criteria_met` は記録上の判定、`hardware_criteria_met` は実機ドメインの記録上の判定。
このプログラムは記録の真偽、動画、ファイルの存在・ハッシュを検証しない。
公開時には必ず根拠マニフェストと生データを別途照合する。

## シミュレーションの現状診断

```bash
python evaluate.py --checkpoint runs/walk_lp40/best \
  --config configs/walk_goal_probe.json --commands 0.1 \
  --episodes 20 --seed 60000 --out outputs/goal_baseline/evaluation.json
```

これは現在の方策を100秒・0.10 m/s指令で調べる診断であり、新プロトコルの受入試験ではない。
旧 `is_success` は旧品質基準の判定で、10 m到達判定ではない。
既存評価は10 mの初回到達で終了せず、接触の終了判定も方策周期で行う。
新受入ランナーでは物理サブステップごとの接触ラッチ、初回到達時刻、
熱・電源・通信保護モデル、両脚の連続歩行記録が必要。
実機の保護停止を未実装のシミュレーションから「なし」と推定しない。

診断の要約とハッシュを保存する:

```bash
python validation/capture_goal_baseline.py \
  --evaluation outputs/goal_baseline/evaluation.json \
  --checkpoint runs/walk_lp40/best \
  --out validation/goal_baseline/diagnostic.json
```

途中経過には `evaluation.partial.json` を指定でき、その記録は `INCOMPLETE` と表示される。
同じ方策の再現には記録に示したSHA-256のチェックポイントが必要。
現在のリポジトリには学習済みチェックポイントを含めておらず、第三者による
方策の完全再現用の配布整理は未完了。

## 比較する量

同じ設計・方策のシミュレーションと実機について、成功数、10 m到達時間、
前進量、転倒・接触・停止理由、関節角／速度、電流、電圧、温度、IMU、着地時刻を比較する。
時刻同期・座標系・センサー遅延を明記し、未計測の項目は欠測とする。
フィッティングに用いた試行と、受入・比較用の未使用試行を分離する。
